# 모바일 HTML 학습 앱 요구사항 명세서

버전 1.0   작성일 2026년 10월 12일   가칭 HTML Study

이동 중 받은 HTML 학습 파일을 아이폰에서 실행하고, 문제를 풀거나 HTML, CSS, JavaScript 소스를 수정할 수 있는 앱을 만든다. 첫 버전은 단일 HTML 파일의 실행과 편집에 집중한다. 개발자와 디자이너는 아래 요구사항 ID와 인수 기준으로 구현 완료 여부를 판단한다.

## 1 제품 목표와 해결할 문제

사용자는 Mattermost에서 HTML 모의고사를 받았으나 미리보기를 실행하지 못했고, 파일 앱에서는 문서처럼 보여 채점 기능을 사용하지 못했다. 앱은 파일을 보관하는 기능과 실제 웹 콘텐츠를 실행하는 기능을 제공해 이 흐름을 해결한다.

핵심 목표는 파일 가져오기, 문제 풀이, 소스 수정, 재실행, 수정본 내보내기를 PC 없이 완료하는 것이다. 문제의 채점 기준과 해설은 HTML 파일이 가진 기능을 그대로 실행한다.

## 3 첫 버전의 범위

필수 P0는 첫 출시의 완료 조건이다. 포함 기능은 파일 앱과 공유 메뉴를 통한 가져오기, HTML과 내장 CSS 및 JavaScript 실행, 기본 소스 편집, 명시적 재실행, 초안 저장, 해당 파일의 저장소 유지, 수정본 내보내기, 오류 확인이다.

추가 P1은 외부 CSS와 JS를 포함한 ZIP 프로젝트, 찾기와 바꾸기, 자동 완성, 가로 화면 분할이다. 계정, 클라우드 동기화, AI 채점, 협업 편집, Java와 서버 코드 실행은 첫 버전에서 제외한다.

### 실행 대상의 의미

앱은 HTML 파일 안에 있는 채점 기능을 실행한다. 채점 코드가 없는 문서에 정답이나 점수를 자동으로 추가하지 않는다. 주관식 채점도 원본 파일에서 지원하는 범위만 제공한다.

화면에 코드 예시로 적힌 문자열은 자동 실행하지 않는다. 모의고사의 문제에 제시된 코드와 페이지의 실제 실행 스크립트를 구분한다.

### 파일 지원 조건

첫 버전은 UTF-8 단일 HTML과 내부 style 및 script, 파일 내부에 포함된 이미지 데이터를 지원한다. 외부 파일이나 CDN, 서버 API에 의존하는 콘텐츠에는 누락 또는 연결 필요 안내를 제공한다. 백엔드, Node.js, JSP 및 빌드 도구는 실행하지 않는다.

### 저장 상태 표시

편집기에는 변경 있음, 저장 중, 저장됨, 저장 실패를 구분해 표시한다. 저장됨은 디스크에 기록된 뒤 표시한다. 적용 전 변경분이 있으면 실행 화면에서 미적용 변경이 있음을 알린다.

강제 종료 직전의 아직 저장되지 않은 입력까지 보장하지 않는다. 저장 완료 상태 이후의 복원은 첫 버전 인수 기준으로 검증한다.

### 기본 흐름

Mattermost에서 파일 공유 또는 파일 앱에 저장 → 앱으로 가져오기 → 실행 화면에서 문제 풀이 → 소스 탭에서 수정 → 적용하고 실행 → 수정 결과 확인 → 파일로 내보내기.

### 학습을 이어 하는 흐름

실행 화면에서 다른 앱으로 이동 → 앱에 복귀 → 기존 웹 화면이 살아 있으면 그대로 이어 한다. 앱이 종료되었으면 페이지를 다시 실행하고 해당 파일의 localStorage를 복원한다. 저장 기능이 없는 임의 HTML의 답안과 DOM 상태는 앱이 일괄 복원하지 않는다.

### 모바일 조작 기준

세로 화면에서는 실행과 소스를 탭으로 전환한다. 키보드가 나타나도 커서와 적용 버튼에 접근할 수 있어야 한다. 앱 조작 버튼은 44 × 44pt 이상으로 설계하며, 긴 코드는 가로 이동을 지원한다. 시스템 글자 크기와 밝은 화면 및 어두운 화면 설정을 지원한다.

원본 HTML의 디자인은 기본적으로 유지한다. 모바일 대응이 없는 파일에는 확대와 가로 스크롤을 제공하며 앱이 임의로 DOM이나 스타일을 재작성하지 않는다. 앱의 어두운 화면 설정이 원본 HTML의 색상까지 변경한다는 보장은 하지 않는다.

### 예외 흐름

빈 파일은 내용 없음으로 안내한다. 인코딩을 해석하지 못하면 깨진 텍스트를 자동 저장하지 않는다. 저장 공간 부족이면 원본과 기존 실행본을 유지한다. 파일 삭제는 확인을 받으며, 삭제되는 소스와 해당 파일 학습 기록의 범위를 명시한다.

| 데이터 | 내용 | 보존과 초기화 |
| --- | --- | --- |
| Document | 문서 ID, 표시 이름, 원본명, 가져온 시각, 최근 열람, 콘텐츠 해시 | 이름 변경에도 ID 유지. 새 사본은 새 ID 발급. |
| Source | 원본 바이트, 편집 초안, 마지막 실행본, 인코딩, 리비전 | 원본은 읽기 전용. 적용 시 실행본을 갱신. |
| WebStorage | 문서 ID별 localStorage 키와 값 | 재열람과 소스 수정 시 유지. 명시적 초기화와 파일 삭제 시 제거. |
| ViewState | 편집 커서, 편집기 스크롤, 실행 화면 스크롤 | 열람 보조 정보로 저장. 답안 상태로 취급하지 않음. |

### 파일별 저장소 분리

경로가 다르다는 이유만으로 localStorage가 분리된다고 가정하지 않는다. 문서별 독립 실행 출처 또는 실제로 분리된 웹 데이터 저장소 등으로 격리한다. 동일 저장 키를 사용하는 두 파일과 앱 재시작 테스트를 통과해야 저장 방식이 확정된다.

이름 변경은 학습 기록을 유지한다. 사본 생성은 소스만 복사하고 학습 기록은 비운다. 내용 해시는 중복 확인에 사용하며 문서 ID를 대신하지 않는다. 저장소 브리지 방식을 택하면 getItem, setItem, removeItem, clear, key, length와 오류 동작을 검증한다.

### 기준 모의고사의 상태 복원

기준 파일에는 답안, 검토 표시, 채점 여부, 시작 시각과 마감 시각을 localStorage에 저장하는 코드가 있다. 앱은 이 값이 유지되도록 실행 환경을 제공한다. 파일 자체의 초기화 버튼은 원본 코드에 따라 동작한다.

타이머는 원본 파일의 60분 정책을 따른다. 앱이 백그라운드에서 매초 코드를 실행하도록 요구하지 않는다. 복귀 또는 재실행 시 원본의 마감 시각 계산으로 남은 시간을 보정하고, 만료되었으면 파일의 자동 채점이 실행되어야 한다. 임의 HTML의 모든 타이머에 같은 복원 기능을 보장하지 않는다.

### 소스 변경 시 학습 기록

기본값은 기존 저장소 유지다. 문항 구조를 바꾼 경우 기존 답안과 맞지 않을 수 있으므로 재실행 전 현재 기록 유지 또는 초기화를 선택할 수 있게 한다. 앱은 HTML을 분석해 문항 변경 여부나 정답을 추정하지 않는다.

## 8 실행 구조와 비기능 요구사항

### 구현 방향

iOS 우선 구현을 권장한다. 네이티브 파일 가져오기와 공유 확장, 앱 내부 파일 저장, 소스 편집기, WKWebView 실행 화면을 연결한다. WKWebView는 앱 내부에서 HTML, CSS, JavaScript 콘텐츠를 표시할 수 있다. 프레임워크 선정과 최소 iOS 버전은 초기 호환성 검증 후 확정한다.

웹페이지 형태의 시제품을 먼저 만들 수 있으나, iOS 공유 메뉴에서 파일을 받아 실행하고 저장하는 요구사항은 실제 아이폰 앱에서 별도로 검증해야 한다. 화면 시제품과 설치 가능한 앱을 같은 완료 상태로 취급하지 않는다.

### 외부 코드 실행의 경계

HTML 실행 환경에는 임의 파일 읽기, 앱 설정 변경, 앱 계정 접근 기능을 노출하지 않는다. 필요한 메시지 통신은 문서 ID와 허용 명령을 검증한다. 카메라, 마이크, 위치 및 임의 URL 스킴 요청은 첫 버전에서 허용하지 않는다.

외부 통신 허용 상태에서도 CORS나 브라우저의 보안 정책을 우회하지 않는다. 외부 리소스가 차단되어 화면이 일부 달라지면 이유를 표시한다. 사용자 HTML이나 답안을 서버로 자동 전송하지 않는다.

## 12 아이폰 설치 전 시연 방법

### 추천 방법은 웹 시연판

웹 시연판을 HTTPS 주소로 배포한 뒤 아이폰 Safari에서 접속한다. 파일 앱에 내려받은 HTML을 문서 미리보기로 여는 방식과 달리, 시연판의 파일 선택 버튼으로 HTML을 읽고 실행 영역에서 동작시킨다. 일반 웹 서버에 파일 선택으로 읽는 것만으로는 파일이 자동 업로드되지 않으며, 소스나 답안을 서버에 보내는 기능이 필요하면 별도 동의를 받도록 구현한다.

웹 시연판에서 확인할 수 있는 것은 해당 웹 구현의 동작이다. Safari에서 정상이라고 해서 WKWebView 기반 설치 앱에서도 동일하게 정상이라고 판정하지 않는다.

| 방식 | 필요한 환경 | 확인할 수 있는 범위 | 별도 검증이 필요한 항목 |
| --- | --- | --- | --- |
| PC 브라우저에서 모바일 크기로 보기 | Windows PC와 브라우저 | 화면 배치, 버튼, 일반 입력, 기본 코드 실행 | 실제 아이폰 키보드, 터치, iOS 공유, 설치 앱 실행 |
| 아이폰 Safari에서 웹 시연 URL 열기 | 아이폰과 접근 가능한 URL | 실제 터치와 한글 키보드, 웹 파일 선택, 웹 구현의 실행과 저장 | 앱 공유 확장, WKWebView 저장 격리와 앱 수명 주기 |

PC에서 모바일 화면 크기를 선택하는 기능은 화면 크기를 바꾸는 도구다. iPhone 운영체제를 실행하는 Simulator와 구분한다.

### 아이폰 Safari 시연 순서

1. 시연 URL을 Safari에서 연다.
2. `파일 가져오기`를 누르고 파일 앱에 저장한 sample.html을 선택한다.
3. 답안을 선택하고 채점한다. 취소 대화상자, 점수와 해설 표시를 확인한다.
4. 소스 탭에서 한글 제목이나 CSS 색상을 바꾸고 적용한다.
5. 저장 완료 표시 후 페이지를 다시 열어 웹 시연판의 저장 동작을 확인한다. 앱이나 브라우저가 저장 데이터를 삭제하는 조건에서는 보존이 달라질 수 있다.
6. 같은 저장 키를 사용하는 두 HTML 파일을 번갈아 열어 값이 섞이지 않는지 확인한다.
7. 수정본을 내려받고 PC 브라우저에서 실행한다.

첫 접속부터 오프라인 실행까지 원하는 경우, 웹 시연판에는 앱 화면과 실행 자원을 미리 보관하는 오프라인 기능을 따로 구현해야 한다. 웹페이지를 한 번 열었다는 이유만으로 오프라인 지원이 완료된 것으로 판정하지 않는다.

### 웹 시연판의 완료 기준

- HTML 파일 선택부터 문제 풀이와 소스 편집까지 사용자가 직접 조작할 수 있다.
- JavaScript 실행과 localStorage 지원 여부를 실제로 확인한다. 지원되지 않으면 원인을 명시한다.
- 시연판에 저장된 학습 데이터와 iOS 앱에 저장된 데이터는 별도다. 자동으로 이어진다고 표시하지 않는다.
- README에 웹에서 통과한 검사, 실패한 검사, iOS 실기기에서 남은 검사를 나눠 기록한다.
- FR02의 iOS 공유 확장과 설치 앱 기준의 인수 테스트는 웹 시연으로 통과 처리하지 않는다.

## 13 설치형 iOS 앱 확인 방법

### Mac과 Xcode를 사용할 수 있는 경우

1. iOS 프로젝트를 Xcode에서 연다.
2. 우선 실행 대상을 iPhone Simulator로 선택하고 Run을 눌러 화면과 웹뷰 실행을 확인한다.
3. 실제 테스트는 아이폰을 Mac에 연결하고 기기와 컴퓨터의 신뢰 설정을 완료한다.
4. Xcode에 Apple 계정을 추가하고 프로젝트의 Signing & Capabilities에서 서명 팀을 설정한다.
5. 실행 대상을 연결한 아이폰으로 선택하고 Run을 누른다. 빌드와 서명이 성공하면 기기에 앱을 설치해 실행한다. 기기와 OS에 따라 Developer Mode 같은 추가 설정이 필요할 수 있다.
6. Mattermost와 파일 앱의 공유 메뉴, 앱 종료 후 답안 복원, 키보드와 파일별 데이터 격리를 확인한다.

Simulator는 Xcode에 포함되어 있다. 일반적인 공식 Xcode 개발 흐름은 Mac에서 진행한다. Windows 브라우저의 모바일 보기로 대신 판정하지 않는다.

### 직접 Mac을 준비하지 않고 실제 아이폰에서 테스트하는 경우

개발자가 준비한 빌드를 TestFlight로 전달받는 방법이 있다. macOS 빌드 환경과 앱 서명 및 App Store Connect 준비가 먼저 필요하며, TestFlight 배포에는 Apple Developer Program 가입이 필요하다.

테스터의 절차는 `아이폰에 TestFlight 설치 → 초대 링크 열기 → 테스트 앱 설치 → 기능 확인`이다. 앱 소스 파일을 TestFlight에 넣는 것만으로 설치 가능한 앱이 되지는 않는다. 빌드 업로드, 처리, 테스터 설정과 필요한 베타 검토를 완료해야 한다.

Mac 환경을 아직 준비하지 않았다면 웹 시연으로 제품 흐름을 먼저 확인하고, iOS 프로젝트와 서명 및 배포 환경이 준비된 뒤 실기기 테스트를 진행한다.
